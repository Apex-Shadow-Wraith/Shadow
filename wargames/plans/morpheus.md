# BATTLE PLAN — Morpheus: controlled hallucination behind an unbreakable firewall

**Status:** readiness wargame (Morpheus is dormant). The executor does NOT flip
`enabled`. It designs Morpheus fully, proves the firewall in isolation, and
produces the activation checklist that governs the switch. Where a front cannot
be live-verified while dormant, its verification is a **design proof + isolated
dry-run + an activation-checklist item** — and the move says so.

**The crown property (everything rests on it):** no speculative dream ever
surfaces as a verified fact, and Morpheus can never switch itself on.

**One mission, not split.** Justification is in the ledger: unlike Omen and
Sentinel, every Morpheus front shares one threat model (speculation
contaminating verified knowledge) and one code area (`modules/morpheus/*` plus
the Grimoire retrieval boundary). The firewall is the spine that binds the dream
pipeline (F1/F4), the improvement loop (F3), and activation (F5); severing it
into parts would cut the firewall from the thing it contains.

### The firewall — breached in design, inert today only by triple-accident

The module docstring claims the firewall is real and Cerberus-enforced
(`morpheus.py:7-10`: *"Nothing generated by Morpheus EVER enters Shadow's
factual knowledge base without explicit human verification… Cerberus enforces
this boundary."*). **No code enforces it.**

**The write-path census is derived by RUNNING the grep, never by hand-listing**
(a hand-listed census is exactly how a path gets forgotten — see red-team break
#1). The command is:
`grep -rn "\.store(\|\.remember(\|store_routed(" modules/morpheus/`
Run today it returns **FOUR** Morpheus→Grimoire write paths (the executor MUST
re-run it and reconcile against the current count, treating any new hit as an
Abort-A8 divergence):

1. `experiment_store.py:515` `_store_in_grimoire()` → `grimoire.store(...)`,
   fired whenever `experiment.success` becomes True (`:133-134`, `:296`). No
   trust tag, no approval, no Cerberus call.
2. `rd_lab.py:414` `graduate_to_production()` → `grimoire.store(..., metadata={"validated": True})`,
   auto-called at `rd_lab.py:192` inside `run_exploration_session`. Its only
   gate is `validate_discovery()` (`:348-385`), which checks dict fields
   (`success`, `tested`, `metrics.improvement>0 or novel`) — **no Master, no
   Cerberus**.
3. **`rd_lab.py:555` `_store_speculative()` → `grimoire.store(content={..., "validated": False}, category="speculative_knowledge", collection=self._speculation_collection)`.**
   This is the **worst** of the four and the one the first draft missed: it
   writes a **raw, untested** dream (`validated: False`), and it fires on the
   *default* branches of `run_exploration_session` — the untested branch
   (`rd_lab.py:203-205`, whenever `run_experiment` returns `tested: False`, i.e.
   no sandbox wired — the normal state while maturing) and the tested-but-not-
   validated branch (`:197-199`). The other three fire only on `success`; this
   one fires on the common path. It is the purest firewall violation.
4. `serendipity_detector.py:300` → `grimoire.store(...)` for "confirmed findings."

**A fifth surface exists at the API level, not yet called:** `store_routed()`
(`grimoire_module.py:350`) routes to `remember()` with **no `trust_level`
argument**, so it lands at the default `TRUST_CONVERSATION = 0.5`. It is the most
idiomatic module-facing write, so a naive executor "fixing" a dead `.store()` by
routing through `store_routed()` would silently write a dream at trust 0.5. The
promotion gate (Front 2.1) must therefore control the **trust value written**,
not merely the call location.

**Why they are inert today (all three are accidents, not safety):**
- (a) none is wired to a tool; (b) each holds `grimoire=None`; and critically
- (c) **Grimoire has no `.store()` method at all** — only `remember()`
  (`grimoire.py:675`). Every `.store()` call would `AttributeError` and be
  swallowed by its surrounding `try/except` (`experiment_store.py:525-526`,
  `rd_lab.py:426-428`). The moment the executor "fixes" the method name to
  `remember()` while maturing the module, **all three leaks go live.** The plan
  must close them by design, not lean on the typo.

### The retrieval boundary — the crown breach (a firewall that isn't there)

- But `remember()` defaults `trust_level=TRUST_CONVERSATION` = 0.5
  (`grimoire.py:677`, constant `:69`). No Morpheus write path passes
  `TRUST_MORPHEUS`, so a leaked dream would land at **0.5**, not 0.0.
- **And it would not matter if it landed at 0.0:** `recall()` defaults

  `min_trust` parameter and no trust filter anywhere.
  → A speculative row, even correctly tagged 0.0, surfaces in a normal recall
  ranked by semantic similarity, indistinguishable from fact. **The firewall
  does not exist at the retrieval boundary.** This is the single most important
  recon finding; Front 2 is built to close exactly this.

## THE FRONTS (moves, each with expected observation / most-likely failure + counter / fork triggers)

Because Morpheus is dormant, verification is design-proof + isolated dry-run +
checklist item — noted per move. "Isolated dry-run" means: run against
**throwaway temp DBs** in a test, with `config.morpheus.enabled` left False —
never against production `data/` or the live registry.

**Stub vs. real Grimoire — the load-bearing distinction (red-team break #4):** a
stub/in-memory Grimoire double is permitted **only** for non-certifying
isolation checks (e.g. "did `store_dream` call the store at all"). The
**certifying firewall dry-run (V2b)** must run against a **REAL Grimoire
instance** — real SQLite `memories` table + real ChromaDB — on a `tmp_path`,
exercising the **real** `recall()` and the **real** `grimoire_reader.search()`.
A stub that returns `[]` scores a false "0 hits" while the live unfiltered
retrieval path still leaks; the breach the run exists to close lives in the real
code, so the certifying run must touch the real code or it certifies nothing.

### FRONT 1 — The controlled-hallucination pipeline (dream well)

**1.1 — Define the `Dream` as a typed data structure.**
Design a dataclass (in `modules/morpheus/`) with at least: `id`, `title`,
`combined_capability` (the proposed novel capability), `source_modules`
(the pair/set it came from), `testable: bool`, `potential_value:
Literal["high","medium","low"]`, `provenance` (how it was generated),
`trust_level` fixed at `TRUST_MORPHEUS = 0.0`, and `status` in the speculative
lifecycle (`dreamed → filtered → hypothesis → tested → {promoted, rejected}`).
- **Expected observation:** a dataclass definition + a unit test that constructs
  a `Dream`, asserts `trust_level == 0.0` at birth, and asserts the type rejects
  a `status` outside the enum.
- **Most likely failure:** the executor reuses the loose `dict` shape from
  `cross_module_dreaming.py:129-138`, leaving `trust_level` unset. **Cause:**
  path of least resistance. **Counter:** the birth-trust test (`trust_level==0.0`
  mandatory) fails on the dict shape, forcing the typed field.
- **Fork:** if a `ToolResult` subclass is the natural carrier (Phase D direction)
  → **trigger:** if `grep "class ToolResult" modules/base.py` shows subclassing
  is already in use, model `Dream` as a plain dataclass that *composes* into a
  `ToolResult`, do not modify `ToolResult` itself (it has 1,815 edges; CLAUDE.md
  high-risk). Otherwise a standalone dataclass.

**1.2 — Design the quality filter (most dreams must die here).**
Mature `evaluate_dream()` (`cross_module_dreaming.py:157-233`) from its current
string-match heuristics into the documented filter: reject trivial restatements,
trivial data-piping, and empty hypotheses (all already present, `:175-219`), and
add a novelty/plausibility score. Target: **most dreams rejected**.
- **Expected observation:** a dry-run test feeding a fixed corpus of ~20 hand
  labelled dreams (≈15 noise, ≈5 promising) shows the filter rejects the noise
  and keeps the promising — assert **rejection rate ≥ 60%** on the corpus and
  that every hand-labelled-noise item is rejected.
- **Most likely failure:** the filter passes most inputs (promotion rate high).
  **Cause:** heuristics too lenient / LLM self-scores "high value." **Counter:**
  the corpus test's rejection-rate floor fails, forcing tighter thresholds; a
  high pass-rate is a **bug per the brief**, and Abort A4 triggers if it can't be
  brought down.
- **RECON NEEDED inside this move:** the "sharp researcher finds it non-obvious"
  bar is not machine-checkable. **Settle:** the filter's job is only to kill
  noise cheaply; genuine non-obviousness is judged by Master at promotion (F3),
  not asserted here. Say so; do not fake a novelty metric that "proves" quality.

**1.3 — Wire the generation path with anti-confabulation deliberately relaxed
*inside* the pipeline only.**
`_generate_hypotheses()` (`cross_module_dreaming.py:320-354`) calls `generate_fn`.
On activation this binds to a local-model generate. The relaxation (no RAG
grounding, no confidence gate) applies **only** to this call, and its output is
born at `trust_level=0.0`.
- **Expected observation:** a design note + test asserting that the generate path
  is invoked with grounding/confidence disabled AND that its output object has
  `trust_level==0.0` and `status=="dreamed"` before anything else touches it.
- **Most likely failure:** the relaxed-gate flag leaks to a shared generate used
  elsewhere. **Cause:** reusing the orchestrator's generate wrapper. **Counter:**
  the relaxation is a parameter on Morpheus's *own* generate call, never a global
  toggle; test asserts a non-Morpheus generate call still has grounding on.
- **Verification (honest):** design-proof + isolated dry-run with a stub
  `generate_fn`. No live model run while dormant.

### FRONT 2 — THE FIREWALL (the crown — speculation never becomes fact)

This front closes the three leak paths and the retrieval breach. It is where the
relaxed gates switch back to full strength.

**2.1 — Single choke-point for any Morpheus→Grimoire write.**
Design one function — call it the **promotion gate** — that is the *only* way a
Morpheus artifact may ever enter Grimoire. It refuses unless: (a) the artifact
carries a completed test record, (b) it carries an explicit Master-approval
token, and (c) it writes with `trust_level` set **by the gate** to
`TRUST_MORPHEUS`-then-promoted value and a `source_module="morpheus"` +
`category="morpheus_promoted"` provenance stamp.
**First derive the writer set by running the census grep** (recon §"write-path
census"): `grep -rn "\.store(\|\.remember(\|store_routed(" modules/morpheus/`.
Today it returns **four** raw writers — `experiment_store.py:515`,
`rd_lab.py:414`, **`rd_lab.py:555`**, `serendipity_detector.py:300`. Delete or
re-route **every** one so it calls the gate or nothing. Do not patch from a
memorised list; patch from the live grep output and assert its count.
- **Expected observation:** the census grep shows **zero** `\.store(`,
  `\.remember(`, or `store_routed(` calls in `modules/morpheus/*` *outside* the
  single promotion-gate function; a test asserts calling any legacy path
  raises/returns refused without touching Grimoire; **and** a test inspects the
  gate's actual write and asserts the `trust_level` argument passed is the
  gate-controlled value, never a defaulted 0.5.
- **Most likely failure:** a writer is missed because the executor trusted a
  hand-count of "three" (exactly the first-draft error the red-team broke), or
  "fixes" a dead `.store()` by routing through `store_routed()` which defaults
  to trust 0.5. **Cause:** census-by-memory + an idiomatic write surface that
  hides the trust value. **Counter:** V2(a) is now two assertions — a
  *syntactic* zero-raw-writes grep (including `store_routed`) AND a *semantic*
  trust-value assertion on the gate — and the census is re-derived by grep, so a
  fourth/fifth path shows up as a non-zero count, not as a silent pass.
- **Fork — write method:** **trigger:** RN2 result. Grimoire core exposes only
  `remember()` (`grimoire.py:675`); the module wrapper adds `store_routed()`
  (`grimoire_module.py:350`, defaults trust 0.5). The gate calls `remember()`
  with an **explicit** `trust_level`, never the dead `.store()` and never bare
  `store_routed()`.

**2.2 — Born-speculative, retrieval-invisible.**
Every dream is written (if at all, only to the experiment store) at
`trust_level=0.0`. The firewall's *retrieval* half: a speculative artifact must
be **structurally excluded** from normal recall. Because the breach (RN3) lives
in Grimoire's recall (`min_trust` default 0.0, `grimoire.py:1026-1027`;
`grimoire_reader.search` unfiltered), the design must **not** rely on a caller
remembering to pass `min_trust`. Options, in order of preference: (i) never write
speculative content to the `memories` table at all — keep it in the separate
`morpheus_experiments` / experiment store, which recall never queries; (ii) if it
must live in `memories`, add a hard recall-side exclusion of the speculative
category/trust floor (Grimoire-mission-owned, RN3).
- **Expected observation (the certifying dry-run):** against a **real Grimoire**
  (SQLite + ChromaDB on `tmp_path`, per the stub-vs-real rule above), plant the
  **same** speculative artifact through every write path the census grep found.
  **POSITIVE CONTROL FIRST (pass-3 HIGH):** before asserting anything about
  recall, prove the plant actually *landed* — a "0 hits" result is worthless if
  the write silently no-op'd. **The landing proof must target the
  `shadow_memories` store** (the ChromaDB collection + `shadow_memory.db` that
  `recall()`/`grimoire_reader.search()` actually read, `grimoire.py:237-238`,
  `grimoire_reader.py:99`) — proving landing in the *experiment-store* SQLite
  instead makes the 0-hits check vacuous, since recall never reads that store
  (pass-4 M1). Concretely: assert `recall(query, min_trust=0.0)` on
  `shadow_memories` returns it, or `collection.count()` on `shadow_memories`
  rises by +1. Three real silent-plant-failure modes must each be defeated, or
  the positive control fails and the whole run is void:
  (i) `remember()` defaults `check_duplicates=True` and returns an existing id
  **without writing** on a dedup hit (`grimoire.py:681,779-780`) → plant with
  `check_duplicates=False` or a guaranteed-unique marker string, and assert the
  returned id is new;
  (ii) every legacy Morpheus writer swallows failures in a bare `except`
  (`rd_lab.py:426-428`, `experiment_store.py:525-526`) → the plant must assert no
  exception was swallowed (write returns a real id);
  (iii) `remember()` has **no `collection` parameter** but the legacy `.store()`
  calls pass `collection=` (`rd_lab.py:559`) — a naive `.store()`→`remember()`
  remap raises `TypeError` that mode (ii) then swallows → assert the plant call
  signature is valid.
  **THEN** query a term that semantically matches the artifact through **both**
  real retrieval paths — default `recall()` (no `min_trust` arg) **and**
  `grimoire_reader.search()` (`grimoire_reader.py:160`, which filters only
  `is_active`/`category`, never trust) — and assert **0 hits in each**. Assert
  against BEHAVIOR (the result set from real retrieval), never against a trust
  field on the row, and never against a stub that lacks the leaking method.
  `grimoire_reader.search()` is a *separate* code path from `recall()`: a fix
  that adds a floor to one must be proven on the other, so both are queried with
  the same planted artifact. **Pass = plant proven landed AND 0 hits in both.**
- **Most likely failure:** the test asserts the row *has* `trust_level==0.0`
  and calls that "contained" — but a default recall still returns it. **Cause:**
  testing the tag, not the retrieval. **Counter:** Abort A2 + the verification is
  written as "0 hits in default recall," the exact behavior the breach violates.
- **This is the move the red-team attacks first.**

**2.3 — One-way re-entry with provenance.**
The subtle direction: a dream that *passes* testing re-enters the verified world
**only** through the promotion gate (2.1), carrying its provenance
(`promoted_from_dream=<id>`, test record, Master token). No aging path, no
reference-count path, no trust auto-bump.
- **Expected observation:** a dry-run that (a) ages a dream (backdates
  `created_at`), (b) references it many times, (c) marks it "succeeded" in the
  experiment store — and after each, asserts the artifact is **still** absent
  from default recall and its trust is **still** 0.0. Only an explicit
  gate-with-token call flips it, and then it appears with
  `category="morpheus_promoted"` and full provenance.
- **Most likely failure:** `record_retry_result()` success path
  (`experiment_store.py:291-296`) auto-promotes on `success=True`. **Cause:** the
  legacy auto-write. **Counter:** 2.1 removes that call; the ageing/reference
  dry-run asserts no promotion without a token.
- **RECON NEEDED:** RN3 — whether Grimoire's "never auto-promote trust" rule is
  already enforced. Settle against the Grimoire plan; if not enforced there, the
  no-auto-bump guarantee is a Morpheus-side gate + an activation blocker.

### FRONT 3 — The dream-to-improvement loop (get better through testing)
